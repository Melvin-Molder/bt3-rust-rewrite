# BT3 Recomp

An original Rust implementation intended to read data from a user-provided copy of Dragon Ball Z: Budokai Tenkaichi 3. The repository contains no game assets or decompiled game code.

## Data-loading proof

The `bt3-data` crate reads the ISO9660 primary volume descriptor and root `SYSTEM.CNF`, then locates and interprets real game resources in the AFS archives. It converts the three loading-screen resources (global file IDs `0x3C1`–`0x3C3`) to in-memory RGBA textures and reads stage gameplay metadata from stage file `0x171`. Run its inspector from the workspace root:

```powershell
cargo run -p bt3-data --bin bt3-inspect
```

By default it reads `rom/Dragon Ball Z - Budokai Tenkaichi 3 (USA) (En,Ja).iso`; pass another ISO path as the first argument to override it. The ISO path reader resolves nested directories, and the AFS reader seeks directly to requested entries rather than loading the 1.46 GB archive. The global file-ID mapping, loading-screen behavior, stage layout, and coordinate transforms are grounded in the decomp sources listed below. Packed data, decoded resources, and RGBA textures stay in memory and are not extracted to disk.

Run the Bevy prototype with `cargo run -p bt3-game`; it accepts the ISO path as its first argument as well. By default it plays the boot pictures of `FirstRun_Main`: the six logos from menu archive `0x1DA`, at 60 Hz, with the original timing, fade colours and skip rules (Space / Enter or a gamepad's South / Start as pad 0 Cross / Start). Before them the memory-card check runs as `BootCard_Run` does: over a black screen the boot load flow looks for the system save on the card and loads it, or offers to go on without one. After them it plays the opening movie as `Movie_Run` does: `DATA/ZS3USOP.PSS` streamed from the ISO through `ffmpeg` (which must be on `PATH`) at one picture per two NTSC fields, with the `DATA/ZS3USOP.ADX` soundtrack decoded in Rust and played at the original's -12.9 dB; Start skips it with a half-second fade. Then it runs the title screen as `Title_Run(1)` does: the still picture for 300 frames, then the title movie (a FOD file, the game's converted Flash format) played by a port of the game's Flash player (`src/sys/flash.c`), with the scrolling clouds, the menu plates, the "Press START button" plate and the New Game / Continue menu (arrows or the d-pad move the cursor, with the original key repeat). The title music (`0x10B16`) loops at -12.9 dB, the announcer lines play at -5.1 dB (voice players 4 / 5 have gain 0x46), and both fade out by 12 dB a frame as the screen fades. `--title` starts there directly. Sound effects play as the game's sound driver plays them: the bank files (`0x14B`, `0x14C`) are read from the ISO, their SE sequences, timbres and ADPCM samples drive an emulated SPU2 (pitch, Gaussian interpolation, ADSR, volume and pan follow Sony's `modsesq2` / `modhsyn` modules from the disc and the psx-spx hardware notes). New Game opens the memory-card dialog of `McFlow_Start(3)` (ports of `src/sys/dialog.c`, `src/sys/memcard_flow.c` and the text printer `src/sys/font.c`, with both fonts of boot file 5); Left / Right move between Yes and No. With the emulated card (below), "Do you wish to create a save file?" → Yes writes the new save to it; No asks "Start a new game without saving?", whose Yes leaves for the main menu. The battle then starts as `Battle_Main` does (src/battle/battle.c): `Battle_Load`'s loading screen runs (with `Load_RunBlocking`'s one-second fade-out once the files are read) while the two fighters' model files (`0x590 + chara * 10 + costume`), the stage file and the light ramp of common file 2 are read; the battle music (`0x10B16 + bgm`) starts, and every 30 Hz frame the fighters are drawn as `BtlObjDraw_DrawModel` and VU1 program 0 draw them (and, for the 73 models with a seam section, `ObjSeam_Draw`'s CPU-skinned triangles between the parts): the model parts' VIF streams are walked into VU1 memory, each batch's triangle strip is transformed, lit (u = 0.5 + 0.5 · −L·n with the stage's light) and projected on the CPU with the battle view's matrices, and drawn by a shader that does the GS's work (perspective-correct STQ, the model texture, then the shading ramp looked up through the material's CLUT and subtracted with ALPHA_2 0x62); which parts are drawn follows `BtlObj_IsNodeShown`: the model's part layout class and the object's part flags pick the weapon nodes (animation events 0x20 / 0x40, bits 43 / 44), node 0x6F (ability 0x79 with parameter flag 0x200000, `BtlFx_UpdateObjFlag80`), the hidden arms of a layout-A technique and node 0x76 of the damaged look. The object keeps its colour preset (`BtlObj_SetColorPreset`: the parameter's row at init, the aura kind with the aura colour abilities after a model change, in the model's table), which the colour modes blend with. The colour modes (`BtlObj_SetColorMode`, by priority into the object's colour flags) change a fighter's draw as `ObjDraw_SetLight` and `ObjDraw_AddClutPass` do: the light from the camera for a model of flag 0x1000000 or the power-up look, the palettes brightened by the colour preset in the power-up look (mode 6), lerped towards pink by a technique's mode 2 (flag 0x8000, fading in by tenths) with the light turning to the camera, the texture unshaded during the transformation's flash (mode 3), and the colour flash of requests 0x1D..0x1F (yellow, white, strong white for a fifth of a second). The stage tint (`StgTint`, four colour layers ramping between two colours) darkens the stage behind the fighters while a fighter's request 0x12 holds (requests 0x10 / 0x11 of the techniques, in the stage file's colours when it has a tint section) and while a rush shot is attached, and turns the screen white behind the fighters for the transformation's flash; slots 2 and 3 are drawn over everything. The weather, storm, smoke, geysers and reflecting surfaces darken with it. Over everything in the effect pass come the blinding overlay (`EftBlind`: grey, as strong as player 0's blind level) and the full-screen flash (`EftFlash`, one at a time: fade in, hold, fade out; the white flash of a fighter swapping to its damaged variant holds until the swap is done and no rush finish is half way). After the effects and before the HUD the frame can be redrawn through itself (`StgFx_DrawPost`): the renderer runs a chain of cameras that copy the frame at half size into two 256 x 224 work buffers, draw them into each other and back over the frame (the HUD gets a camera of its own after them). The scene is drawn by two cameras, the stage's and then the fighters' (which draws the stage's depth again first, depth only, as the GS keeps it), with a second chain of post cameras between them for `StgFx_DrawPre`. Over the stage, before the fighters, the passes read the spare byte above the 24-bit depth, which `GfxDepthFog_Draw` fills from the depth itself (the depth page read as 16-bit pixels, each word's low half written 8 pixels on into the frame's high half under the write mask, then drawn through a 255 - index ramp where the depth is below 0xFFA8): `255 - (Z >> 8)`, 0 nearer, 255 for the sky. A camera of its own draws that byte from the stage's depth-writing groups each frame, and the depth tint (`StgDepthTint`, stage section +0x40: the air's, or under the water level the water's, never in split screen) draws it through its CLUT, the stage's colour added by its curve or blended with its curve as alpha. The sky glare (`StgGlare`, section +0x48 with bit 0) weighs the frame by its CLUT (0x80 for the sky's byte, the record's alpha elsewhere) into a half-size buffer over black, shrinks it to an eighth, passes it ten times between two eighth-size buffers (each read only within its own texels, as the GS's region clamp reads), grows it back tinted by its level and adds it over the frame; with the record's bit 1 the level rises by its step while the stage light's point is on the view (to its maximum, then settling to the hold level) and falls by 1 to its minimum while it is not, else it stays at the maximum. The depth fog filter (`StgFog`, section +0x50 with bit 0) copies the frame at half size and stretches it back blended by its curve's CLUT (the sky's byte clear by the record's bit 1): a blur that grows with depth. The pan blur (stage flag 8) follows each view's camera (full screen: fighter 0's): a sideways move of 1 .. 2.5 or past 4 units a frame raises its strength by 0.1, else it falls by 0.15; the half-size copy is shrunk again with two copies shifted toward the side the camera turns, then stretched back weighed by `0x80 - byte / 2` times the strength (the original carries that alpha through its shrunk copies; here the last blend applies it). A post op can be blended by such a CLUT's alpha of the byte under each pixel, which is how the GS's destination-alpha blend reads it. The depth haze (`StgHaze`, stages 3 and 19: section +0xA0 with bit 0) copies each view at half height and draws it back through a grid of strips whose texels jitter toward targets drawn with libc `rand()` (two a point every period, not while paused, from the shared stream), blended by its curve's CLUT, at full strength on the ground and half at the stage's top by the camera's height; as in the original only view 0 gets the stage's curve, and a strip's lower vertex takes the next column's offset. After the effects comes the underwater wobble (`GfxWater`: while a view's camera is below the water level of a stage whose water record has bit 0, the view is copied at half height into the 512-wide work page and drawn back opaque, tinted with the record's colour, through a grid that two cosine waves push around). The radial blur uses it too (`StgBlur`: the copy zoomed in over three passes, drawn back as two rings of strips whose alphas are its strength), raised by a fighter's requests 9 / 0xA (`BtlFx_UpdateScreenFilter`, e.g. the homing dash) and by the techniques: a blast, prop shot or steered dash (`EftFollow_UpdateLight`) with definition flag 0x200 between its blur events, a connected rush shot or shot technique between the victim's events 0x10 and 0x20. So do the screen shock waves (`ScrWarp`): each ring redraws the frame's half-size copy through a strip to a jittered middle and one beyond it, so the picture warps where the ring passes. The view is a fighter camera (`ChrCam_Update`: the lock-on, free and fixed cameras with their swing, the shake, the smoothing; side 0's unless the other has a cut with the screen, flag 0xD3) or the demo camera. Each fighter loops its idle motion (motion 0 of its motion file `0x598 + chara * 10`, BPE-packed, two frames per 30 Hz update as `BtlAnim_AdvanceLoop` steps it): the tracks are sampled as `BtlObjAnim_SamplePose` does (packed "smallest three" quaternions, slerp, rest translations), the motion flag table of common file 2 is applied, and the node matrices are built down the model's skeleton as `BtlObjPose_CalcMatrices` does, so every part is skinned between its node and its parent. Before the fighters, the stage is drawn as `StgModel_Draw` draws it: the stage object of the stage file gives seven draw groups of materials and meshes, the meshes the culling tree and the never-culled list can reach once `BtlStage_Reset` has put the destructible objects back whole, and the stage texture file; each mesh's VIF chain is run through an emulation of VU1 program 4 (transform, clip test, and the Sutherland-Hodgman clipper that turns crossing triangles into fans), and the groups are drawn with their GS states (alpha blending, the alpha tests of groups 0 / 1 / 2, no depth writes for the sky and the blended groups) in the original order, stage first. The battle opens as `BtlSeq` runs it, under `Battle_Restart`'s one-second fade-in: the stage intro plays the stage file's three camera cuts (`DemoCam_PlayStageAnim`, keyed camera tracks evaluated as `DemoCam_EvalAnim` does), then the intro talk puts each fighter in turn into its entrance (action 1: motion `0x180` once, then `0x181` looping) under the entrance camera of its model file (section `0x29`, attached to the fighter's root node) while its line plays (`Voice_PlayChara`, special lines from the talk table of section `0x16` for known pairings, a random one of two otherwise), then Ready resets both fighters to their starting places, shows the HUD's READY announcement after 0.8 s and FIGHT as it ends (`HudNotice_Show`: the sprite sheets of HUD file 6, the word revealed through a turning band that the GS keeps in the destination alpha, the fragments flying out, the streak added through the word's alpha, and the announcer's lines `0x10B6C + announcer * 7` on streamed-SE player 0; the finishes draw theirs the same way: K.O. popping with after-images and a red streak, the other K.O. on an opening band, the spinning words, the winner's word zooming in behind its copies and the result's lower banner; mode 7, the attract demo, draws only `HudCaption`'s two sprites, the lower one pulsing). Player 1's button prompts come up as `HudPrompt_*` draws them: the button the key config gives an action (pulsing base, the font icon sheet's animated button, the glow dropping onto it) while a mash or change prompt flag is raised, the struggle's mashing picture, and the row of direction, plus and button of the technique the fighter watches, which grows and fades when it is performed. With Ready the HUD's gauges and clock come on as `HudGauge_*` and `HudTimer_*` draw them: each side's face (character file section 1), health in bars of 10000 with the markers of the bars in reserve, ki in bars of 20000 with the lamp of the bar just gained, the blast stock, the powered-up sparks and flashes, the status icons of the stat modifiers (fading out, sliding and fading in as they change), the face tinted in colour mode 2, all mirrored for side 1, and the clock counting down the rule's time limit (`gBattleTimeLimitTbl`, read from the game's ELF: none, 60, 90, 180, 240 or 45 s) or showing infinity. The starting values come from the character table of common file 2 (health 40000 and ki 40000 for Goku, 6 blast stocks). Their masks live in the GS's alpha plane (destination alpha tests, alpha tests that keep the RGB, FBA, write masks), so these sprites are drawn by a small emulation of the GS pixel pipeline into a layer composited over the frame. Each cut ends with `ScrXfade`'s one-second cross-fade: the last frame is kept in a second frame buffer and drawn over the following frames as it fades out. Start skips the current part as `BtlPause_CheckStart` does. After the intro the fight runs as described under the handoff status below. The hair, tails and cloth bend as `btl_obj_chain.c` bends them: the chains of character file section 0x17 (type A with stiffness, rest pull, inertia and hinge limits; type B in a plane between yaw limits) follow the fighter's movement, the stage's wind and a logistic-map noise, and the pushes and sway the ki charge, the techniques' charge loops and recoils, the clashes, the transformations and the rush sequences give them. The head and neck turn towards the opponent's head as `btl_head_tracking.c` turns them: within the windows that start and keep the tracking (taken in the head's parent frame, so a fighting stance's turned chest can leave it off), clamped to the limits after the chain parameters of section 0x17, half the rotation on each node, eased in while a guarding, standing or moving action looks and out otherwise, reset at a technique's or transformation's start. The faces move as `BtlObj_UpdateFace` moves them: the eyes blink every 90..179 frames for 3..5 (libc `rand()`, in `BtlObj_UpdateAll`'s place after the cameras), or hold a frame the tired idle or a motion event forces; the mouth talks a random pattern for a voice line of the fighter's own bank, follows the line's lip track (character file entries 0x99.., the fresh save's voice set) for a streamed line, the intro and win talk, and holds the shapes the low-health idle and motion events ask for. A shape replaces the mouth part with its mesh (entries 4..11), shapes 5..8 and the eye frames (entries 0xE.., 0xD) the face texture, and a jaw model turns node 0x31 along one of the executable's jaw tracks. Each battle records both fighters' input (`BtlReplay_Record`, up to 9000 frames); View Replay Data on the result menu restarts it with the replay playing (`BtlReplay_Play` feeds the recorded input back, the replay's own pause and result menus, pad 0's left / right choosing whose camera is shown and up / down the HUD's replay mode: the caption, everything with the replay mark, or nothing; no vibration or blind overlay) until its input runs out.
